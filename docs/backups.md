# Backup and restore drill
Run scripts only after k3s is deliberately installed and tools available. Configure `RESTIC_REPOSITORY=s3:https://cos.na-ashburn.myqcloud.com/BUCKET-APPID/restic/cloudlab`, RESTIC_PASSWORD, AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY from the new 1Password items. Never put the env file in Git. `restic init` is a one-time operator action against the future bucket. Run `sudo --preserve-env=RESTIC_REPOSITORY,RESTIC_PASSWORD,AWS_ACCESS_KEY_ID,AWS_SECRET_ACCESS_KEY,KUBECONFIG ./scripts/backup.sh` with the k3s kubeconfig path supplied. Requires restic, python3, kubectl, flock and node-local access.

Schedule daily at 03:20 UTC using a root systemd timer after a successful drill. Load a mode-0600 env file from 1Password after reboot; keep it outside the backup allowlist. Nothing is installed or scheduled by this task. Restic retains snapshots within 30 days and prunes; versioned deleted COS packs can consume space for another 35 days. No age-based expiration of live restic objects. Check disk and COS growth weekly; check restore monthly. Single node means downtime during disk/node failure, not HA.

The script exports only the `apple-health` bucket as annotated query CSV, and creates an online SQLite backup of Kuma then sanitizes it. This is intentionally data-only: Influx users/tokens are re-created from 1Password. Kuma user/session/notification/unknown tables are cleared; monitor credential fields are blanked and URL userinfo/query removed. Review new Kuma schema and ensure URLs/descriptions/tags contain no embedded secrets before each upgrade. Sanitization may remove integrations; reconfigure from 1Password. No raw PV copies, Git, container images, cluster state, secrets, or kubeconfigs go to COS. Grafana configuration/dashboards should be provisioned from Git; later UI-only data must receive an explicit sanitized exporter, never blanket disk backup.

Drill on an isolated namespace/node without public HTTPRoutes:

1. `restic snapshots --tag cloudlab`, `restic check`, then `restic restore SNAPSHOT --target /data/restore-drill`; inspect the restored nested staging directory. Never restore over live PVs.
2. Deploy a separate InfluxDB 2.7 instance and initialize new auth from 1Password. Convert the query CSV to line protocol with an audited CSV parser: group annotated CSV blocks, preserve measurement, tags, field type and nanosecond `_time`. Do not feed query CSV directly to `influx write` (its annotations are query-specific). Then `influx write --bucket apple-health --org cloudlab --precision ns --file health.lp`. Compare measurement counts, timestamps and sample values. A reusable importer is supplied as `scripts/restore-health.py`.
3. Stop the drill Kuma deployment, copy sanitized `kuma.db` into its fresh `/app/data` PVC, set ownership to its image UID, start; complete fresh admin setup and re-enter monitor credentials/notifications from 1Password. Compare monitor count and history. Never merge WAL from a previous database.
4. Record snapshot ID, exported row counts, app checks and elapsed recovery time in a dated drill note. Delete the isolated drill only after success. Target RPO 24h; RTO must be measured, not assumed.

Influx query export: https://docs.influxdata.com/influxdb/v2/query-data/execute-queries/influx-cli/ . Native backup/restore is documented at https://docs.influxdata.com/influxdb/v2/admin/backup-restore/ but is excluded here because full metadata includes auth state.
